## 2. 问题诊断

### P0-1 概念错位：有"聚类"，没有"区域"

`dbscan.js` 返回的结构是：

```js
{ clusters: [[point, point, ...], ...], noise: [point, ...], clusterCount, noiseCount }
```

**全是点集合，没有任何几何面。** 而"地理区域智能划分"的本质是：把一片地理空间**切分成 K 个有明确边界的片区（polygon）**，每个片区是一块**地面**。

由此产生三个直接后果：

| 后果 | 说明 |
|---|---|
| 无法指定片区数 K | DBSCAN 由密度自动决定簇数，业务上"我要把市区分成 10 个片区"做不到 |
| 无法做容量均衡 | 没有任何机制保证各片区业务量相当 —— 这恰是区域划分最核心的业务诉求 |
| 结果无法在地图上画 | `ClusterPage` 只用文字列表展示"区域 1 / 包含 N 个点 / 中心位置"，分片结果从没上过地图 |

### P0-2 空数据库，项目不可演示

见 §1.3。没有数据，算法、地图、页面全是空转。这是**半天就能修好、但收益最大**的一件事。

### P1 工程化缺失

| 项 | 现状 | 影响 |
|---|---|---|
| 版本管理 | **不是 git 仓库** | 无法回溯、无法开源、作品集不成立 |
| SQL 注入面 | 手写字符串拼接 `SELECT * FROM items WHERE type = ?` 实际用了参数绑定，尚可；但建表与查询混在 `index.js` | 单文件 323 行，无分层 |
| 依赖 | `ol`（OpenLayers 9）在 `package.json` 中，**代码里零引用** | 死依赖，历史遗留（早期试过 OpenLayers 后换高德） |
| 环境变量 | `.env` 与 `.env.local` 都写了 `VITE_AMAP_KEY`，但 `index.html` 直接硬编码 | env 形同虚设，key 暴露 |
| 测试 | 无 | 算法改动无回归保障 |

## 3. 关键洞察：把业务事件变成划分权重

这是我认为这个项目**真正该做、但一直没做出来**的东西。

现在项目里有 4 类带地理坐标的业务事件：闲置物品、寻物启事、紧急医疗、区域讨论。它们目前只被当作"4 个平行的 CRUD 模块"，和"区域划分"是**两张皮**。

但换个角度 —— **这些事件天然就是区域划分的权重来源**：

| 事件类型 | 密集意味着什么 | 应投放的资源 |
|---|---|---|
| 急救事件 | 该片区突发医疗需求高 | 医疗志愿者 / AED 布点 |
| 闲置物品 | 该片区交易活跃 | 物流运力 / 自提点 |
| 寻物启事 | 该片区失物高发 | 失物招领点 / 巡逻 |
| 区域讨论 | 该片区居民参与度高 | 社群运营 |

于是划分目标从"让每个片区**面积**相等"升级为"让每个片区的**服务负载**均衡"——这正是 §4.3 中容量约束聚类的业务含义。

**闭环由此成立：**

```
业务事件产生数据 → 数据驱动区域划分 → 划分结果指导资源投放 → 投放产生新的业务事件
```

这个闭环在面试上能讲满 5 分钟，而且它就是你原项目真正想做、但被 DBSCAN 挡住没能做出来的东西。**这是本项目最大的升值空间。**

### 4.3 算法升级：DBSCAN 降级为四种之一

**不要删掉 DBSCAN，而是把它放进 baseline 阵营。** 它有价值：能识别噪声点、不需要预设 K。缺的是"生成片区边界"。

| 算法 | 角色 | 边界生成方式 |
|---|---|---|
| `dbscan` | baseline 1（现有代码） | `ST_ConvexHull` 凸包，或 `ST_Buffer(ST_Collect(pts), r)` |
| `grid` | baseline 2 | 等距网格本身就是面 |
| `plain_kmeans` | baseline 3 | 质心 → Voronoi |
| **`capacity_kmeans`** | **主算法（新增）** | 质心 → `ST_VoronoiPolygons` → 与市域边界 `ST_Intersection` 裁剪 |

**主算法四步（承接 v1 设计，已按现有代码调整）：**

```
P0 预处理   坐标统一 GCJ-02、去重、剔除市域外点
P1 初始化   加权 k-means++（按业务量权重采样）
P2 再分配   容量感知贪心（按权重降序安置）→ move/swap 局部搜索
            目标 J = J_dist + λ·J_balance + μ·J_shape，硬约束：归属唯一 / 容量上下限 / 空间连通
P3 边界     ST_VoronoiPolygons → ST_Intersection(市域) → ST_Buffer(0) 修自相交 → ST_SimplifyPreserveTopology
P4 评估     业务量 CV / 平均·P95 服务半径 / Polsby-Popper 紧凑度 / 跨行政区率
```

性能目标：`n=5000, K=20` 单次 < 3s（近邻剪枝 + 候选点筛选）。

### 4.4 数据模型

现有 `items` 单表 + `type` 字段的 discriminated 设计是合理的，保留并扩展：

```sql
-- 业务事件（现有 items 表演进）
CREATE TABLE event (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  type       text NOT NULL,          -- secondhand | lostfound | emergency | discussion
  title      text NOT NULL,
  category   text,
  weight     numeric(10,3) NOT NULL DEFAULT 1,   -- 新增：业务量权重，由事件类型与紧急度派生
  status     text NOT NULL DEFAULT 'active',
  geom       geometry(Point, 4326) NOT NULL,      -- 由 latitude/longitude 两列改为空间列
  created_at timestamptz DEFAULT now()
);
CREATE INDEX idx_event_geom ON event USING GIST (geom);

-- 划分方案 / 片区 / 归属（新增，结构同 v1）
plan(id, name, algorithm, params jsonb, status, metrics jsonb, created_at)
territory(id, plan_id, seq, centroid geometry, total_weight, event_count, area_km2, geom MultiPolygon)
assignment(plan_id, event_id, territory_id, distance_m)
```

坐标列从 `latitude REAL / longitude REAL` 改为 PostGIS `geometry(Point)` —— 这是换 PostGIS 最大的收益之一：能建 GIST 索引，"点落在哪个片区"从 O(n·K) 降到 O(log n)。

- **对比实验** `api/scripts/benchmark.py`：随机 / 等距网格 / 纯 k-means / 容量约束方法 四基线，K=5/10/20 × 5 种子。结论见 §7.2。

### 7.2 算法对比结论（800 事件 / 北京 / λ=2.0）

| 方法 | CV(业务量)↓ | 平均半径(m)↓ | 超容片区↓ |
|---|---|---|---|
| **容量约束（本方法）** | **0.18–0.34** | 2.4k–5.7k | **0** |
| 纯 k-means | 0.59–0.64 | 1.1k–3.9k | 1–3 |
| 随机 | 0.09–0.19 | ~10k | 0 |
| 等距网格 | 1.27–1.42 | 1.5k–7.6k | 1–6 |

**杀手锏**：本方法是唯一满足容量硬约束（超容=0）且业务量均衡（CV≈0.2）的方案；k-means 半径略优但完全不顾业务量（CV 0.6）且违规。λ 为可调权衡参数（λ↑→更均衡、半径↑）。

## 8. 优化实施（对齐原始蓝图的质量标准）

用户提供的项目原始蓝图（2024 生成历史）点名了若干工程质量标准，而 Trae 实际生成的代码**因技术栈降级（React/高德 取代 Vue/Cesium/OpenLayers、Node/SQLite 取代 SpringBoot/GeoTools/GDAL）且一路出 bug 回退**，这些标准都没落地。本轮把原始蓝图的**工程质量标准**应用到当前能跑的栈上（不推翻已定的 FastAPI + 高德决策）：

### 8.1 海量地理数据加载优化（原话：「分页查询、数据点抽稀」）
- **数据量级放大**：造数器默认 800 → **4000** 事件（北京 10 热点），让"海量"成为真实约束；算法 n=4000 / K=10 实测 **1.96s**（目标 <3s）。
- **点抽稀（WebGIS 标准做法）**：新增 `GET /api/items/aggregate?bbox&grid`，按 grid×grid 经纬网格把视窗内事件聚成**密度桶**（质心 + 计数 + 总权重 + 类型分布）。
  - 实测：整城 3995 点 → **296 个聚合桶**，前端 DOM 标记从数千压到数百，彻底消除卡顿。
  - 前端 `TerritoryPage` 按 **zoom + 视窗点数** 自动切换：低 zoom / 点数 > 400 → 渲染聚合桶（抽稀视图）；高 zoom → 走明细。
- **分页查询**：`GET /api/items` 新增 `offset/limit/bbox`，返回 `{total, count, items}`；明细视图按视窗 bbox 分页拉取，避免一次性返回上万条。

### 8.2 组件化拆分 + 跨组件数据交互（命中 JD「独立开发通用 UI 组件」）
从 `TerritoryPage` 抽取三个**与业务解耦、props 驱动**的通用组件到 `frontend/src/components/`：
- `MetricPanel.jsx`：通用指标面板（schema 驱动，可复用于任何数值指标墙）
- `BenchmarkTable.jsx`：通用对比实验表（方法行数组 → 横向对比）
- `RegionChipList.jsx`：通用片区/标签清单（与地图配色一致，可点击联动）
- 父子通过 props 传递数据（划分结果 → 各组件），体现"组件间数据交互"。

### 8.3 后端分层 + 接口规范（对齐「controller-service-dao / 制定接口规范」）
- 现有分层：`routers`（路由/接口契约）→ `services`/`algorithms`（业务逻辑）→ `models`/`schemas`（数据模型）。
- 接口统一前缀 `/api`，划分类走 `/api/territory/*`，文件兼容层走 `/api/items`（保留旧契约）。
- 注：原蓝图后端为 **SpringBoot + GeoTools + GDAL**，我们因已定 **FastAPI** 决策未采用；分层思想一致，具体框架按当前栈落地。
