## 一、背景与设计目标

当前系统已实现"可用"：FastAPI + PostGIS 生产链路跑通、4 算法对比、Voronoi 边界裁剪北京行政区、深色 GIS 控制台 UI、3D 负载柱体、可分享链接。但它目前是"功能正确"而非"让人眼前一亮"。

本设计的目标是让产品从**可用 → 出彩**，核心叙事一句话：

> **让城市服务资源跟着真实需求走。**

所有改造围绕这条主线，分四层推进（视觉 / 交互 / 业务 / 叙事）。

## 二、现状点评（数据依据）

### 2.1 已具备的优势（护城河，保留）

1. **业务闭环真实**：4 类事件（闲置/寻物/急救/讨论）密度 = 片区服务负载，划分目标从"面积相等"升级为"负载均衡"——区别于纯地理聚类玩具 demo。
2. **算法有深度**：4 算法对比 + 评估指标（cv_weight / capacity_violations / compactness / radius）。
3. **生产级架构**：FastAPI + SQLAlchemy + PostGIS，Voronoi 边界 `ST_VoronoiPolygons` + 北京裁剪 `ST_Intersection`。
4. **GIS 视觉雏形**：深色控制台、定位框、准星、坐标 HUD、指北针、比例尺。
5. **可玩性**：参数市场（K/λ/类型/种子）、3D 柱体、分享链接。

## 五、接口改造点（后端，精确到字段/函数）

### 5.1 `RegionOut` 增强 —— 让每个片区"说得清"

文件：`api/app/schemas/territory.py:33`

```python
class RegionOut(BaseModel):
    region_id: int
    weight: float
    point_count: int
    centroid: list[float]
    polygon: Any | None
    # —— 新增 ——
    type_breakdown: dict[str, float]   # 各类事件权重占比，如 {"secondhand": 1200.5, "emergency": 300.0, ...}
    capacity: float                    # 片区承载上限（总容量 / K 推导，或配置项）
    load_ratio: float                  # weight / capacity，>1 即过载
    overload: bool                     # load_ratio > 1
    suggested_action: str | None       # "OK" / "拆分" / "合并" / "新增服务点"
```

实现位置：`territory.py` 的 `divide_endpoint`（第 188-206 行循环内），用 `res.assignment == r` 的掩码对每个类型分别求和即得 `type_breakdown`；`capacity` 由 `total_weight / k * 1.2`（留 20% 余量）推导。

### 5.2 `DivideResponse` 增强 —— 输出"决策建议"而非裸指标

文件：`api/app/schemas/territory.py:41`

```python
class DivideResponse(BaseModel):
    k: int
    lam: float
    method: str = "capacity-constrained"
    metrics: dict
    regions: list[RegionOut]
    geojson: dict
    source: str = "database"
    # —— 新增 ——
    balance_report: dict | None        # 见下
    recommendation: dict | None        # {"method": "capacity-constrained", "reason": "...", "cv_improvement_pct": 0.41}
```

`balance_report` 结构（在 `divide_endpoint` 末尾计算）：

```json
{
  "ideal_cv": 0.18,            // 理想均衡下的 cv（等权假设）
  "current_cv": 0.37,
  "improvement_pct": 0.51,     // (ideal_cv - current_cv)/ideal_cv 的相对改善（演示用对比基线即可）
  "overload_count": 0,         // regions 中 overload=true 的数量
  "verdict": "负载均衡良好，无片区超容"  // 人话结论
}
```

### 5.3 `BenchmarkRow` / `BenchmarkResponse` 增强 —— 标注推荐算法

文件：`api/app/schemas/territory.py:51`、`territory.py:231`

```python
class BenchmarkRow(BaseModel):
    method: str
    cv_weight: float
    mean_radius_m: float
    max_radius_m: float
    mean_compactness: float
    capacity_violations: int
    # —— 新增 ——
    is_recommended: bool = False
    rank: int | None

class BenchmarkResponse(BaseModel):
    k: int
    rows: list[BenchmarkRow]
    recommended_method: str        # 综合 cv 最低 + violations=0 的算法
```

实现：`benchmark_endpoint` 计算完 `rows` 后，按 `capacity_violations==0` 且 `cv_weight` 最小排序，给最优行打 `is_recommended=True` 并填 `recommended_method`。

### 5.4 时间维度 —— 让数据"活"起来（P0 核心）

**现状**：`Event.created_at` 字段已存在（`event.py:62`），但 seed 时所有事件时间戳均为 `func.now()`（同一时刻），无法做时间回放。

**改造步骤**：

1. **造数器/seed 播种时间戳**：在 `api/scripts/` 或造数器 CLI 中，为每个事件分配 `created_at`，分布到过去 N 天（如 7 天），并按真实日周期加权（白天寻物多、夜间讨论多、周末闲置多）。
2. **`DivideRequest` 增加时间窗**（可选，向后兼容）：
   ```python
   time_window: dict | None = Field(default=None, description="{'start': ISO, 'end': ISO}，按时间切片重划")
   ```
   在 `_load_points_from_db`（第 112 行）加 `where Event.created_at.between(start, end)`。
3. **新增时间片序列接口**（支撑滑块回放，避免每次拖动打后端）：
   ```python
   # territory.py
   @router.get("/timeseries")
   def timeseries_endpoint(k: int = 6, lam: float = 2.0, mu: float = 0.1,
                           seed: int = 42, steps: int = 12):
       """按时间均分切成 steps 片，逐片滚动重划，返回 [{t, geojson, metrics, regions}, ...]。"""
   ```
   前端时间滑块选 index → 直接 `renderRegions(series[idx])`，丝滑回放。

### 5.5 字段变更对照表

| 接口                        | 原字段                | 新增字段                                                                           | 前端消费点            |
| ------------------------- | ------------------ | ------------------------------------------------------------------------------ | ---------------- |
| `POST /divide`            | regions[].weight 等 | regions[].type_breakdown / capacity / load_ratio / overload / suggested_action | 片区清单 → 负载卡片；异常预警 |
| `POST /divide`            | metrics            | balance_report / recommendation                                                | 均衡报告卡            |
| `GET /benchmark`          | rows[]             | rows[].is_recommended / rank；recommended_method                                | 对比表加推荐徽标         |
| `GET /timeseries`（新）      | —                  | 时间序列划分                                                                         | 时间滑块回放           |
| `GET /which_region`（新，P2） | —                  | region_id by lng/lat                                                           | 因果联动弹窗           |

## 九、风险与开放问题

1. **时间戳真实性**：seed 的时间分布是模拟的，演示足够；若接真实业务数据需确认 `created_at` 来源。
2. **timeseries 性能**：steps=12 × 每次完整重划，建议后端缓存或预计算一次返回序列（已设计为单次返回序列）。
3. **容量基线**：`capacity = total_weight/k*1.2` 是演示用启发式，真实场景应由业务 SLA 定义，需与用户确认。
4. **分享链接兼容**：时间滑块状态、算法选择应编码进 URL（现有分享链接机制可扩展）。
